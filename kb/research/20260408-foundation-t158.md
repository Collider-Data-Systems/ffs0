## 1. The Central Triangle

Every mo:os design decision lives inside this triangle. No corner is treated in isolation.

```
Category Theory  <----------->  Hypergraph Rewriting (Wolfram)
       ^                                   ^
       |                                   |
       +------------- mo:os --------------+
                        ^
          Hyperdimensional Computing (HDC / VSA)
```

- **Category Theory** — formal language: objects, morphisms, functors, natural transformations, presheaves. The kernel speaks this natively.
- **Wolfram Hypergraph Rewriting** — computation model: the graph IS the state. Rewrite applications are the only operations. Causal invariance = replay consistency.
- **HDC / VSA (Kanerva)** — representation layer: every graph structure encodes as a hypervector. GPU-parallel algebra over distributed representations.

A **relation** (Wolfram: hyperedge) IS a **wire connecting typed ports** (Spivak operad) IS a **hypervector binding** (HDC). Same object, three views.

## 2. Three-Layer Model

```
+---------------------------------------------+
|  L3: HDC/VSA  (compute + similarity)        |
|  phi(node) = bundling{hypervectors of rels}  |
+---------------------------------------------+
|  L2: Spivak Operads  (grammar / types)      |
|  ports . wiring diagrams . composition law   |
+---------------------------------------------+
|  L1: Wolfram Hypergraph  (runtime)          |
|  nodes . relations . rewrite rules           |
+---------------------------------------------+
```

### Layer 1 — Wolfram Hypergraph (Runtime)

**References:**
- Wolfram Physics Project: wolframphysics.org/technical-introduction/
- Gorard, "ZX-Calculus and Extended Hypergraph Rewriting Systems" (2020)

**Nodes** are identity points in the graph. Identity is defined by the relations a node participates in (Yoneda: an object is fully determined by its morphisms), not by internal fields.

**Relations** are hyperedges — tuples of nodes connected through typed ports. Not binary edges (HyperGraphRAG Proposition 1: binary decomposition is provably lossy).

**Rewrite rules** are the only operations that transform graph state. The Wolfram model has no explicit add/remove node — only hyperedge rewriting. This is foundational for the two-primitive reduction (see section 5).

**Causal invariance** (strictly stronger than Church-Rosser confluence): all orderings of independent rewrite applications yield isomorphic causal graphs. Independent rewrites on disjoint node sets commute.

### Layer 2 — Spivak Operads (Grammar / Type System)

**References:**
- Spivak, "The operad of wiring diagrams" (2013), arXiv:1305.0297
- Fong & Spivak, "Seven Sketches in Compositionality" Ch. 6
- nLab: ncatlab.org/nlab/show/hypergraph+category

**Ports** are named, typed interface points on node types. Port compatibility determines valid wiring. The **operad** is the collection of all valid wiring patterns and their composition rules — in code: `operad.Registry`.

**Port colors** (auth, topology, transport, compute, storage, workflow, semantic, projection) classify ports into compatibility channels. The color compatibility matrix (section 10) governs which source-target color pairs produce valid relations.

**Hypergraph category**: a symmetric monoidal category where each object has Frobenius monoid structure. The full system (operad grammar + hypergraph instance) forms a hypergraph category.

### Layer 3 — HDC / VSA (Compute + Similarity)

**References:**
- Kanerva, "Hyperdimensional Computing: An Introduction" (2009)
- PMC article on HDC: pmc.ncbi.nlm.nih.gov/articles/PMC10588678/

Three operations, each mapping to a mo:os graph operation:

| HDC Op | Symbol | Property | mo:os Mapping |
|--------|--------|----------|---------------|
| **Binding** | x (XOR/Hadamard) | Dissimilar to both inputs; invertible | LINK (relation creation) |
| **Bundling** | + (majority/sum) | Similar to all inputs; superposition | Node state (superposition of incident relations) |
| **Permutation** | pi^k (rotate) | Encodes sequence/position | Rewrite log temporal ordering |

**Wire encoding**: `w = SRC_ROLE x phi(src_urn) + SRC_PORT x phi(src_port) + TGT_ROLE x phi(tgt_urn) + TGT_PORT x phi(tgt_port)`

**Node hypervector**: `phi(node) = bundling{w : w in relations(node)}` — two nodes with similar neighborhoods produce similar hypervectors. GPU similarity search without explicit traversal.

**Morphism log encoding**: `phi(log) = bundling{pi^i(phi(m_i)) : i = 0..n}` — single hypervector encodes entire rewrite history with temporal order preserved.

## 3. Nomenclature

### 3.1 Decision Table

| Concept | Use this | Not this | Layer |
|---------|----------|----------|-------|
| Identity point in graph | **node** | element, vertex, anchor, object | L1 |
| Typed connection between nodes | **relation** | binding, edge, wire, association | L1 |
| Category of a relation | **rewrite category** (WF01-WF17) | named relation, UML association | L1/L2 |
| Interface point on a node type | **port** | slot, endpoint | L2 |
| Valid composition rules | **operad** (or registry) | grammar, schema | L2 |
| Graph transformation operation | **rewrite** | morphism (for the op), update, mutation | L1 |
| Log of all rewrites | **causal graph** | morphism log, event log | L1 |
| Discrete interaction artifact | **interaction node** | transition, event, message | L1 |
| HDC vector multiply | **binding** (HDC only) | — | L3 |
| HDC vector add | **bundling** | — | L3 |
| HDC encoding of a node | **hypervector** / phi(x) | embedding | L3 |
| Node identity | **URN** | SHA hash, content address | all |
| URN reference property | **`_urn` / `_urns`** | `_ref` / `_refs` | all |
| Access control | **permission / capability** | content-addressing | all |
| Typed key-value on a node | **property** | field, payload, attribute | L1 |

### 3.2 Forbidden Terms

| Do not use | Why | Replacement |
|------------|-----|-------------|
| binding (for graph) | Collides with HDC binding operation | relation |
| edge | Implies 2-arity only | relation |
| morphism (for the wire) | Morphism = the rewrite operation | relation |
| object | Implies OOP | node |
| schema (for operad) | Too database-flavored | operad |
| transition (for interaction nodes) | Collides with "state transition" | interaction node |

### 3.3 The Critical Distinction

A **relation** exists because a past LINK rewrite created it. It persists until a future UNLINK rewrite removes it. It does not carry messages, invoke methods, or trigger behavior. It is topology.

A **rewrite category** (WF01-WF17) classifies which operations are allowed, under what constraints, on what port types, with what authority. It is NOT a named static relationship.

## 4. Architecture

### 4.1 Five Planes

| Plane | Contains | Role |
|-------|----------|------|
| Governance | Principal, delegate, capability, policy, promotion | Who can do what |
| Ontology | Shared operad, rewrite categories, invariants | What is valid |
| Instance | Per-kernel realized graph + rewrite log | What exists now |
| Substrate | CPU, GPU, container, storage, network | What runs where |
| Projection | UI, file tree, API, embeddings | Read-only views — **never source of truth** |

### 4.2 Strata

| Stratum | Name | Description |
|---------|------|-------------|
| S0 | Authored | Human-written seeds, design docs, industry data |
| S1 | Validated | Operad-checked, type-approved |
| S2 | Materialized | Hydrated into kernel graph, operational |
| S3 | Evaluated | Concurrent subgraph eval: hypervector encoding, ranking |
| S4 | Projected | UI, filesystem, API — never ground truth |

Every property records its stratum origin. S4 cannot become source of ontology truth.

**Reducibility boundary** (Wolfram section 6): S0-S1 are computationally reducible (deterministic, verifiable). S2+ involves LLM outputs, user actions, emergent topology — partially irreducible.

### 4.3 The Catamorphism

```
state(t) = fold(log[0..t])
```

The append-only log is truth. State is derived. Every rewrite is logged. Any state can be replayed from genesis. This is sigma: Log -> State — a catamorphism (fold), not a functor.

### 4.4 Five Causal Invariants

| ID | Invariant | Formal | Scope |
|----|-----------|--------|-------|
| CI-1 | Church-Rosser commutativity | M_a ; M_b = M_b ; M_a when affected(M_a) intersect affected(M_b) = empty | All rewrites |
| CI-2 | Projection naturality | Project(Apply(M, S)) = Apply(M', Project(S)) for declared structure-preserving projections | Only projections with rewrite correspondence |
| CI-3 | Identity stability | For all M, for all x: urn(M(x)) = urn(x) | All rewrites |
| CI-4 | Log replay determinism | Same log -> same state, always | Per kernel |
| CI-5 | Rewrite category stability | Permitted categories do not change under rewrites — only governance changes the operad | All non-governance rewrites |

CI-2 note: NOT all projections satisfy CI-2. Aggregate projections (counts, rankings, UI composites) are "lossy" — valid for display, invalid as source of truth.

## 5. Rewrite Primitives — The Two-Primitive Model

### 5.1 Implemented: Four Operations

The kernel currently implements four rewrite types:

| Rewrite | What it does | Implementation |
|---------|-------------|----------------|
| **ADD** | Create a new node with typed properties | `fold.Evaluate` with `graph.ADD` |
| **LINK** | Create a new relation (hyperedge) connecting nodes via typed ports | `fold.Evaluate` with `graph.LINK` |
| **MUTATE** | Change one typed property value on one existing node | `fold.Evaluate` with `graph.MUTATE` |
| **UNLINK** | Remove one relation | `fold.Evaluate` with `graph.UNLINK` |

These four are operational in `moos-kernel` (Go, github.com/MSD21091969/moos-kernel) as of T=157.

### 5.2 Theoretical Foundation: Reduction to Two Primitives

**Agreement reached T=158**: The four operational rewrites are theoretically reducible to two fundamental operations: **MUTATE** and **LINK**.

**Categorical precedent:**

1. **Yoneda Lemma** — An object is fully determined by its morphisms (Hom-functor). No separate ADD needed: a node "exists" the moment it participates in relations. ADD is MUTATE from the absent set to the present set of properties.

2. **Wolfram Model** — No explicit add/remove node operation. Only hyperedge rewriting. Nodes emerge from and are defined by the hyperedges they participate in.

3. **Presheaf Toposes** — "All possible nodes already exist" as free cocompletion of the base category. ADD materializes a node from the latent space into the realized graph — this is a MUTATE of the node's existence property from absent to present.

4. **CRDTs (Conflict-free Replicated Data Types)** — Tombstone pattern: deletion is addition of a tombstone marker. UNLINK is LINK to a terminal/tombstone state, not destruction of structure. This preserves the append-only invariant at the relation level.

5. **Double Pushout (DPO) Rewriting** — Two-phase: match (identify the subgraph) then rewrite (delete matched portion + add new portion). Consistent with MUTATE (rewrite existing) + LINK (add new structure).

6. **Mokhov Algebraic Graphs** — Two binary operations (overlay + connect) suffice for all graph construction. Maps to MUTATE (overlay: superposition of node states) + LINK (connect: create relations).

### 5.3 The Reduction

| Current | Reduces to | Mechanism |
|---------|-----------|-----------|
| ADD | MUTATE | Mutation from absent set (empty/null properties) to present set. Only URN is created at the time of the "ADD" — there is mutation from absent properties into the ones needed. |
| LINK | LINK | Unchanged — fundamental. Creates hyperedge. |
| MUTATE | MUTATE | Unchanged — fundamental. Changes property value on existing node. |
| UNLINK | LINK | LINK to "unlinked" / tombstone state. The relation is not destroyed but marked terminal. If hyperedges to and from all nodes conceptually pre-exist (within limits of the algebra), then UNLINK is LINK with a terminal port color or status. |

### 5.4 Implementation Strategy

The kernel internally may operate on 2 primitives. The API can continue to expose 4 for ergonomics and clear error semantics. The 4-to-2 mapping is a section of the API functor — syntactic sugar that desugars to the 2-primitive core. This preserves backward compatibility while making the formal model cleaner.

**Status**: Theoretical agreement. Not yet implemented in Go. The existing /dev documents (categorical-space.md, ptp-binding-categories.md, fiber-decomposition.md) argued for 4 as minimal. The T=158 research provides formal backing for reduction. Resolution: 4 is operationally minimal (clear errors), 2 is theoretically minimal (formal model).

## 6. Two-Presheaf Model

### 6.1 Separation of Concerns

**Agreement reached T=158**: The system operates with two separate presheaves over the same base category K (the category of kernels and kernel morphisms):

```
P1: K^op -> Set    (Structural/Access presheaf)
P2: K^op -> Set    (Knowledge Domain presheaf)
```

**P1 (Structural presheaf)** assigns to each kernel its structural fiber:
- Ownership (who owns this kernel)
- Access permissions (who can write rewrites here)
- Hardware profile (compute, storage, network topology)
- Ontology slice (which types this kernel handles)
- Federation topology (endpoints, shard rules, routing)

**P2 (Knowledge Domain presheaf)** assigns to each kernel its knowledge fiber:
- Content nodes (knowledge items, claims, classifications)
- Classification schemes (LCC, Dewey, domain-specific taxonomies)
- User-authored artifacts
- Extracted/evaluated semantic structures

### 6.2 Cross-User Rewrite

A user writing knowledge to another user's kernel is a section of P2 (the content) authorized by a morphism in P1 (the access permission):

```
rewrite_permitted(actor, target_kernel, envelope) :=
    P1(target_kernel).access_policy(actor) entails envelope.rewrite_type
```

P1 is checked first. If P1 says no, P2 is never consulted.

### 6.3 Restriction Maps

- **P1 restriction**: When kernel A federates with kernel B, structural fibers restrict by intersecting access policies. Write access on A does not imply write access on B.
- **P2 restriction**: Cross-kernel queries pull back knowledge fibers — you see the union of what you're permitted to see, each piece retaining its home kernel provenance.

### 6.4 Implications for Implementation

The `Runtime.Apply()` path needs two validation stages:
1. `validateStructural(env, accessFiber)` — P1 check
2. `validateDomain(env, knowledgeFiber)` — P2 check

Currently there is one `validate()` call. The two-stage split is a future refinement.

## 7. Functorial Semantics

### 7.1 Syntax -> Semantics Functor

**Agreement reached T=158**: The relationship between ontology and graph instances is Lawvere's functorial semantics:

```
[[_]]: Syn -> Sem
```

- **Syn** = category whose objects are ontology types (33 node types, 17 WFs) and whose morphisms are grammatical rules (port compatibility, allowed_rewrites, mutate_scope). This is `ontology.json` — a *theory* in the Lawvere sense.
- **Sem** = category whose objects are graph instances (live nodes and relations in a kernel) and whose morphisms are applied rewrites. This is `GraphState` — a *model* of the theory.

The functor maps each type declaration to its set of instances, and each grammatical rule to the set of valid rewrites. `operad.Registry` + `fold.Evaluate` together ARE this functor.

### 7.2 Stochastic / Bayesian Extension

Not all models are equally likely or useful. Weighting the semantics by usage frequency, confidence, or user preferences gives a **stochastic functor** — it doesn't just say "these instances exist" but "these instances matter this much."

This is where HDC encoding becomes crucial: phi(node) captures neighborhood structure, and weighting is scalar multiplication before bundling.

### 7.3 Multi-Kernel as Multiple Models

The ontology is the *free theory*. Any kernel running that ontology is a *model*. Different kernels can be different models of the same theory — they interpret the same types differently based on their knowledge domain (P2). Functoriality guarantees that if a rewrite is valid in the syntax, its interpretation is valid in every model.

This is why ontology versioning matters: changing the theory changes what all models must satisfy.

## 8. Routing and Federation

### 8.1 Current Implementation

Two Go binaries, zero external dependencies:

- **moos-kernel** (github.com/MSD21091969/moos-kernel): HTTP :8000, MCP SSE :8080, MCP stdio
- **moos-router** (github.com/MSD21091969/moos-router): HTTP :9000, URN-prefix shard routing, fan-out GET merging

Federation live since T=157:
- hp-laptop: kernel :8000, router :9000 (localhost)
- hp-z440: kernel :8000, router :9000 (192.168.1.13)

Router currently uses static CLI flags for shard routing:
```
--shard "urn:moos:ws:hp-laptop=http://localhost:8000"
--shard "urn:moos:ws:hp-z440=http://192.168.1.13:8000"
```

### 8.2 Routing as Graph Traversal

**Agreement reached T=158**: The static shard table is a constant functor — it maps every query to the same fixed routing. The target is a representable functor: the routing table derived from the graph's own federation topology (WF16 nodes: router, endpoint, shard_rule).

```
Route(urn) = coslice(urn_prefix) intersect {nodes of type endpoint}
```

**Migration path**: Keep `--shard` flags as bootstrap seeds only (like DNS root hints). On startup, the router pulls `/state/nodes` filtered to WF16 types, builds its live routing table, and subscribes to `/log/stream` for topology changes. New kernels announce themselves by ADDing endpoint + shard_rule nodes.

This is consistent with the principle: information is in the structure of the network. The shard table becomes a materialized view of the graph, not external configuration.

### 8.3 Content-Addressed Identity

**Discussed T=158**: SHA256 of `(type_id, immutable_properties)` as node URN.

Benefits:
- Deduplication: same concept on two kernels gets same URN, federation merges idempotent
- Integrity: URN IS the hash, tampering detectable
- No central registry needed

Routing governance falls out of the two-presheaf model: P1 handles routing via consensus on the federation subgraph. Each kernel maintains its own P1 fiber. When kernels federate, they exchange P1 sections. Consistency comes from content-addressed URNs — if two kernels independently create the same shard_rule, URNs match, merge is conflict-free.

**Status**: Discussed, not implemented. Current URNs are human-readable (`urn:moos:user:sam`). Migration path TBD.

### 8.4 Federation Sync Contract

| Sync mode | Categories | Semantics |
|-----------|-----------|-----------|
| **Strict** | WF01, WF02, WF13 | Propagate immediately. Conflicts block, require governance. |
| **Eventual** | WF05-WF07, WF11-WF12, WF14-WF15 | Converge eventually. Tie-break: `(event_time, kernel_id, event_id)`. |
| **Local-only** | WF03, WF04, WF08-WF10 | Never leave originating kernel. |

## 9. Multi-Kernel Spawning

### 9.1 The Model

**Discussed T=158**: A workstation (e.g., Z440) runs dozens of kernels for multiple users and agents. Each kernel = own process, own JSONL log, own memory, own ontology slice.

### 9.2 Spawning as a Program

Spawning a kernel is an atomic program (sequence of rewrites):

```
1. ADD  urn:moos:kernel:z440-user-alice       type=kernel
2. ADD  urn:moos:compute:z440-alice-01         type=compute_resource
3. ADD  urn:moos:storage:z440-alice-log        type=storage_resource
4. LINK WF03 kernel -> compute
5. LINK WF03 kernel -> storage
6. LINK      kernel -> ontology_slice
```

A **reactor** (WF17) watching for new kernel nodes fires an effect:
```json
{
  "effect": "tool_call",
  "tool": "spawn_kernel",
  "args": {
    "log_path": "$storage_path",
    "ontology": "$ontology_slice_path",
    "listen": ":$next_port"
  }
}
```

### 9.3 Self-Evaluation

A kernel can MUTATE its own status based on health metrics (memory pressure, log length, query latency). A watcher on kernel status can trigger scaling: spawn a sibling, migrate knowledge, compact log.

Kernel mitosis: overloaded kernel spawns a child, partitions its P2 (knowledge domain), updates P1 (structural fiber), announces the split via ADD of new endpoint + shard_rule nodes. Other kernels learn organically through federation sync.

### 9.4 Ontology Updates

Kernels detect ontology diffs and either hot-reload or spawn a fresh image with new definitions. The ontology is maintained because the hypergraph follows industry conventions and classification systems (see section 11).

## 10. Reactive Layer: Watch / React / Guard

### 10.1 Categorical Interpretation

| Component | Category Theory | Implementation |
|-----------|----------------|----------------|
| **Watch** | Presheaf (observes graph sections) | Pattern matcher on rewrite events |
| **React** | Natural transformation (structure-preserving map) | Template-based rewrite generation |
| **Guard** | Subobject classifier (truth-value filter) | Boolean condition on graph state |

### 10.2 Implementation

Live in `Runtime.Apply()` since T=157. Depth-1 cycle break: reactive proposals do not themselves trigger further reactive evaluation.

```
Apply(envelope) ->
  validate -> fold.Evaluate -> persist -> broadcast ->
  runReactive(persisted) ->
    for each proposal: applyReactiveLocked(proposal)  // no recursion
```

Watcher matching: rewrite_type, type_id, URN prefix, port.
Guard evaluation: node_property, relation_exists, node_exists, negate.
Reactor templates: JSON envelope with $matched_urn, $matched_type_id, $actor substitution.

### 10.3 Node Types (WF17)

| Node type | Properties |
|-----------|-----------|
| watcher | watch_filter (rewrite_type, type_id, urn_prefix, port), status |
| reactor | reactor_template (JSON envelope template), status |
| guard | guard_condition (check, field, expected_value, negate), status |

Connected via WF17 LINK: watcher -> reactor, watcher -> guard.

## 11. Knowledge Domain and Classification

### 11.1 Structure over Content

**Key insight T=158**: The data we extract, evaluate, store, and move is more structure than it is actual files, integers, or PDFs. Structures with conventions — what might be called "IRL metadata": messy but essential when you move real-world information into a hypergraph.

Library systems are conventions. A list of requirements on a git repo is a convention. Ultimately, we are storing users' knowledge and curating it and making it retrievable.

### 11.2 Classification as Knowledge Fiber

Different kernels can use different classification ontologies as part of their P2 (knowledge domain) fiber:
- Library of Congress Classification (LCC)
- Dewey Decimal
- Domain-specific taxonomies
- Industry standards, benchmarks, DSLs

The classification scheme is part of the knowledge fiber, not the structural fiber. Federation across kernels with different classifications requires a **natural transformation** between classification functors — which is exactly what the Embedding functor (HDC) provides: map both schemes to hypervector space, similarity search bridges the gap without requiring a universal taxonomy.

### 11.3 Conventions, Benchmarks, Industry Alignment

The ontology must signal meaning using known conventions. The semantics (bayesian/weighted presentation of the code — the purpose of the machine) must be described in broader terms and applied to what the system does. Purpose must be reflected with known conventions and classifications to signal relevance correctly.

This connects to:
- Weighted programs (Bayesian inference)
- Logic programming
- Industry buzzwords as semantic anchors
- Classification standards as structuring devices

### 11.4 The Manifold Hypothesis Connection

**Flagged T=158, unresolved**: The alignment between user descriptions/prompts and the operadic structures touches the manifold hypothesis — high-dimensional data (user intent, knowledge structures, graph topology) lies on lower-dimensional manifolds. The HDC encoding should preserve this manifold structure. If the morphisms and operadic grammar are aligned with user intent and industry conventions, the encoding manifold faithfully represents the knowledge domain.

This requires further investigation: how do we ensure that our port colors, rewrite categories, and classification schemes span the right manifold? Is there a principled way to derive the operad from the manifold structure of real-world knowledge?

**Relations are truth. Properties never duplicate topology.**

If a fact is expressed as a relation (LINK), it MUST NOT also be stored as a property. The graph topology is the single source of structural truth.

## 14. Property Model

### 14.1 Property Meta Requirements

Every property must declare:

| Meta-property | Meaning |
|---------------|---------|
| mutability | `immutable` (ADD only) or `mutable` (MUTATE allowed) |
| authority_scope | Who can MUTATE: principal, kernel, owner, delegate, capability |
| stratum_origin | S0/S1/S2/S3/S4 origin |

### 14.2 MUTATE Boundary Contract

MUTATE is valid iff:
1. Field exists in allowed_fields for that node type
2. Field is in MUTATE scope for the rewrite category being invoked
3. Field is not globally immutable (URN, created_at, owner_urn, sender_urn)
4. Authority scope is satisfied
5. Validation passes

### 14.3 Topology-Property Boundary

Properties express intrinsic per-node state (what a node IS).
Relations express structural connections (how nodes relate).

**Test**: If information involves two or more nodes, it is a relation. If it involves one node's internal state, it is a property.

**Exception**: `owner_urn` and `sender_urn` are immutable provenance stamps set at ADD time — "birth certificate" data, not topology.

## 16. Operational Semantics Examples

Transport (HTTP, MCP, SMTP, filesystem) is the adapter layer — NOT part of the graph. The kernel normalizes all inbound data into rewrites.

### 16.1 Create a delegate and grant capability

```
ADD  urn:moos:agent:sam.writer
     name="writer" I, owner_urn=urn:moos:user:sam I, delegate_type="llm" I,
     model="claude-sonnet-4-6" M, status="idle" M

ADD  urn:moos:capability:sam.writer.messaging
     scope=["WF07","WF15"] I, granted_by_urn=urn:moos:user:sam I

LINK WF02  [agent:sam.writer] <-> [capability:sam.writer.messaging]
```

Capability check = graph query: find WF02 relations incident to delegate where target is capability node with matching scope.

### 16.2 Session with message exchange

```
ADD  urn:moos:session:sam.writer.T158-001       status="active" M
LINK WF07  [session] <-> [user:sam]              role: principal_participant
LINK WF07  [session] <-> [agent:sam.writer]      role: delegate_participant

ADD  urn:moos:message:sam.T158-001.msg-001       content="Draft intro" I, sender_urn=user:sam I
LINK WF07  [session] <-> [message:msg-001]       sequence=1
MUTATE session.turn_count = 1                    WF07, authority: kernel
```

### 16.3 Reactive chain (live since T=157)

```
MUTATE urn:moos:ki:example .status = "raw"       WF12, authority: kernel

-- Reactive engine fires --
Watcher matches: rewrite_type=MUTATE, type_id=knowledge_item
Guard passes: status == "raw"
Reactor emits: MUTATE urn:moos:ki:example .status = "claim-pending"   WF12
```

## 18. Open Design Questions

### From T=152 (carried forward, still open)

1. **Structural vs emergent**: Do user, agent, kernel remain structural ontology types, or dissolve into emergent port-signature patterns?
2. **Natural transformation as proof**: Cross-provider translation conjectured as NT — verification mechanism?
3. **Principal immutability**: Should principal ownership anchors be globally immutable with zero exceptions?
4. **WF15 governance**: How much structure must a semantic relation carry before warranting a dedicated WF?
5. **CI-2 boundary**: Registry of CI-2-compliant projections vs lossy projections.

### From T=158 (new)

6. **Two-primitive formalization**: Formal proof that MUTATE + LINK generate the same rewriting system as all four. Define the desugaring precisely.
7. **Content-addressed URN migration**: Transition from human-readable URNs to SHA-based. Backward compatibility strategy.
8. **Router bootstrap**: Exact protocol for router to self-derive routing table from graph after initial seed.
9. **Multi-kernel spawning protocol**: Full specification of kernel mitosis including port allocation, ontology slicing, and announcement.
10. **Manifold hypothesis**: How to ensure operad structure aligns with the manifold structure of real-world knowledge domains. Relationship between port colors, rewrite categories, and the intrinsic dimensionality of knowledge.
11. **Calendar as projection**: Time-dependent data (running programs, past/future nodes) as projections with temporal coordinates. Lingo clarification needed — Wolfram speaks of "structures" (relations).
12. **Convention alignment**: Ensuring morphisms and operadic structures align with user prompts and industry conventions (LCC, requirements lists, DSLs, programming languages). The "IRL metadata" problem.
13. **Program node type**: No `program` container node in ontology yet (only `prg_task`). Needed for representing ongoing work as subgraphs.
