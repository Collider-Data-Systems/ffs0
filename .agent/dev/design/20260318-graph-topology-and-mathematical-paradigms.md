# Graph Topology and Mathematical Paradigms

Design doc capturing the formal agreements from the March 18, 2026 session (Sam + Claude Code, Program 2). Establishes the mathematical framework that mo:os operates within, the relationships between competing paradigms, and the evolution path for wire identity.

**References:** [the-carpet](20260314-the-carpet.md), [hypergraph](hypergraph.md), [vision-architecture](20260314-vision-architecture.md), [concepts](concepts.md), [ACT 2026 paper](../reference/papers/act2026/main.tex)

---

## §1 Context and Motivation

mo:os sits at the intersection of three mathematical traditions: category theory, Wolfram hypergraph rewriting, and hyperdimensional computing. Each offers a different lens on the same structure. Until now, the design docs treated these separately — the carpet formalizes the catamorphism, the hypergraph doc proves the König encoding, the paper develops the categorical model. This document unifies them into a single framework and records design decisions about where each paradigm governs.

The immediate trigger: a discussion about wire identity (morphisms have no URN, no stratum, no owner) revealed that the three paradigms disagree on what a "morphism" is. Resolving that disagreement required mapping the full space.

---

## §2 The Superset as Free Category

The ontology (`superset/ontology.json`) is not derived from industry data. It is derived from **expectations about ideal industry behavior**. The superset hovers above industry — rules based on what the industry _should_ look like produce the type structure.

Formally: the superset is a **free category** generated by:
- Objects: OBJ01–OBJ22 (type declarations)
- Morphisms: MOR01–MOR17 (typed wire declarations)
- Subject to: port constraints from the operad (derived from `ontology.json` at hydration time — see [superset-pipeline](20260317-superset-pipeline.md))

Everything below the superset is a **functor out of this free category**:
- `classify : Industry → Superset` — maps external entities to types
- `Include_K : Kernel ↪ Superset` — embeds the 5 kernel colors (see `concepts.md` §Authority Boundary)
- `Σ : Free(Superset) → GraphState` — the catamorphism (fold)
- `FUN01–FUN05` — projections to filesystem, UI, embeddings, structure, benchmarks

In Lawvere's terms: the ontology is the **syntax category**. Instances are **models** (functors from syntax to Set). What industry commonly calls "semantics" (labels, descriptions, embeddings) is actually syntactic decoration. True semantics emerges only when a functor maps syntax to a target category — the kernel's fold, the Explorer's render, the benchmark's metric space.

**Consequence:** The superset changes only when our expectations change, not when the industry changes. Industry changes produce new authored data (S0); superset changes produce new types. These are independent axes.

## §3 Three Models Compared

The kernel's graph structure admits three mathematical readings. All three are correct simultaneously — they are not competing models but different projections of the same structure.

| Aspect | Typed Ports (current kernel) | König Wire-Nodes (HG meta-layer) | Wolfram Rewriting |
|--------|------------------------------|----------------------------------|-------------------|
| **What is a morphism?** | Anonymous 4-tuple wire: `(src_urn, src_port, tgt_urn, tgt_port)` | First-class node in bipartite encoding | Application of a rewrite rule to local subgraph |
| **Wire identity** | Composite key, no URN | Own URN, own stratum, own metadata | Rule application ID (log position) |
| **Ownership** | Source object via port declaration in operad | Wire-node owns itself, participates in both endpoints | Rewrite rule's scope determines affected subgraph |
| **Composition** | Operad port matching (`ValidateLink` 5-step) | Node-to-node morphism through wire-node | Rule composition (DPO spans) |
| **GPU mapping** | Port-typed adjacency tensor | Bipartite incidence matrix | Rulial space exploration |
| **Expressiveness** | Interface contracts between typed objects | Full n-ary hyperedge relations | Emergent topology from rule application |
| **What it's good for** | Governance, validation, type safety | Metadata on relations, wire-to-wire morphisms | Causal structure, multiway branching, replay |

**Current status:** The kernel implements typed ports. The hypergraph doc proves the König encoding is lossless (Proposition 2). The Wolfram reading is implicit in the morphism log. All three coexist without conflict because they operate at different layers.

**Design decision:** Typed ports remain the kernel's internal model. König wire-nodes are a **meta-layer addition** for the HG level (above kernel, below PRG). Wolfram rewriting is the **interpretive framework** for the morphism log.

## §4 The Enforce / Discover Boundary

The five strata split into two regimes:

```
S0 (Authored)   ─┐
S1 (Validated)  ─┤  ENFORCE: typed, operad-constrained, computationally reducible
S2 (Materialized)┘
                  ← boundary →
S3 (Evaluated)  ─┐  DISCOVER: evaluation, projection, partially irreducible
S4 (Projected)  ─┘
```

**Enforce regime (S0–S2):** Every state transition is deterministic and verifiable. The operad's `ValidateLink` checks port compatibility. `ValidateAdd` checks stratum admissibility. Immutability is enforced at two layers: the stratum guard in `evaluate.go` blocks all mutations to S0 nodes regardless of type, and `ValidateMutate` in `validate.go` blocks mutations to types declared immutable at any stratum. Given the same log prefix, replay produces identical state. This is Wolfram's **computational reducibility** — the kernel can predict the outcome without running every step, because the type system constrains the space.

**Discover regime (S3–S4):** Evaluation involves LLM outputs, user decisions, external API responses. The functor outputs (Explorer view, benchmark scores, embeddings) depend on contingent state that the type system cannot predict. This is Wolfram's **computational irreducibility** — you must run the computation to know the result.

**The boundary matters because:**
- Below it: process verification (each morphism validated individually) is sufficient
- Above it: outcome verification (check the final state) is necessary
- The catamorphism `Σ` operates entirely in the enforce regime
- Functors `FUN01–FUN05` cross the boundary — their inputs are enforced, their outputs are discovered

**Connection to the superset:** The free category generates the enforce regime. Everything in S0–S2 is a model of the syntax category. S3–S4 are where models interact with the world outside the category.

## §5 Multiway System and Governance as Observer

The kernel serializes morphism application via `sync.RWMutex` (in `internal/shell/runtime.go`). But the `Scope` field on `Envelope` already hints at causal independence: `Scope` is a single URN (typically a container), serving as a proxy for the affected subgraph. Two morphisms whose affected node/wire sets are disjoint commute — `Scope` approximates this but does not precisely delimit it.

```
LINK(A→B, scope=X) ; LINK(C→D, scope=Y) = LINK(C→D, scope=Y) ; LINK(A→B, scope=X)
    when affected(X) ∩ affected(Y) = ∅
```

This is an **implicit multiway system** in Wolfram's sense. The kernel doesn't branch — it serializes — but the structure supports branching. Three pruning steps collapse the multiway graph to a single timeline:

1. **Operad prune (type):** `ValidateLink` rejects morphisms that violate port constraints. Entire branches of the multiway graph are eliminated before they're created.
2. **Governance prune (authority):** The `Actor` field on `Envelope` + stratum constraints (S0 immutability, promotion rules) eliminate unauthorized branches.
3. **Serialization prune (order):** The `RWMutex` picks one total order from the remaining commutative possibilities.

**Governance as observer:** In Wolfram's physics, observation selects a consistent causal path through the multiway system. In mo:os, governance does the same thing — it selects which morphism sequences are permitted, collapsing the multiway graph to a single realized timeline. Same mathematical effect, different mechanism.

**Church-Rosser property:** For morphisms that pass both prunes and operate on disjoint scopes, the final state is independent of serialization order. This is the graph-level Church-Rosser property. It's what makes replay consistent — any valid total ordering of commutative morphisms produces the same `GraphState`.

**QUIC connection (future):** Independent scopes map naturally to independent QUIC streams. Each stream carries morphisms for one scope; streams are causally independent. This is the network-level realization of the multiway system. Paper-relevant even before implementation.

## §6 IRL Topology and Opaque Leaves

The graph has a natural boundary where typed structure ends and opaque computation begins.

**Opaque leaves:** Docker containers, LLMs, filesystems, user data stores, external APIs — these are functions in their own categories, behind a gate. The graph cannot see inside them. Only the metadata sticker on the gate is visible: a node with ports, a type, a stratum.

```
Graph structure (typed, visible, enforce regime)
    │
    ├── Node: urn:moos:tool:docker-runner (OBJ07, S2)
    │     └── [opaque: Docker engine, own topology, own state]
    │
    ├── Node: urn:moos:model:claude-opus (OBJ06, S2)
    │     └── [opaque: LLM weights, attention mechanism, token stream]
    │
    └── Node: urn:moos:surface:filesystem (OBJ09, S2)
          └── [opaque: directory tree, file contents, OS permissions]
```

**What the graph knows:** Port signatures (what can connect), stratum (governance level), type (operad constraints), payload (metadata sticker). **What it doesn't know:** Internal state, internal topology, execution semantics.

**Code at leaves, graph structure above:** The kernel's Go code lives at the leaves — compiled functions that the graph composes but doesn't introspect. The graph's job is composition, not execution. Execution happens when a functor maps graph structure to a target category (running a program, rendering a view, computing a benchmark).

**Promoted projections:** When a pattern in the graph stabilizes — the same composition of morphisms appears repeatedly, validated by governance, producing consistent results — it can be **promoted** from data (S4 projected pattern) to code (compiled Go in the kernel). This is the `Include_K ⊣ Restrict_K` adjunction growing:

```
Before promotion:  Include_K embeds the current kernel colors
                   (defined in concepts.md §Authority Boundary)

After promotion:   Include_K embeds N+1 colors (+ the newly promoted pattern)
                   Restrict_K now handles N+1 types with compiled struct handling
```

The current kernel colors are a design-level concept — types whose semantics the kernel understands structurally, as opposed to types evaluated uniformly through the 4 NTs. In the current implementation, the operad `Registry` treats all types uniformly via `TypeSpec`; the distinction is architectural intent, not yet a code-level branch. The mechanism is the kernel's growth path — new categories enter as data, stabilize through use, and eventually differentiate into kernel-specific handling.

## §7 Wire Identity: Status Quo and Evolution Path

### Current Model (Typed Ports)

Wires are anonymous. Identity is the composite key:

```go
// From internal/cat/wire.go
func WireKey(src URN, sp Port, tgt URN, tp Port) string {
    return string(src) + "|" + string(sp) + "|" + string(tgt) + "|" + string(tp)
}
```

- No URN for wires
- No stratum for wires
- No direct ownership — derived from source object's port declaration in the operad
- Provenance: `Actor` field on the `Envelope` that created the wire (in the morphism log)
- Multiplicity: multiple wires between same `(A, B)` distinguished by port pairs
- Wires carry an optional `Config map[string]any` field for key-value metadata, but this does not affect identity (WireKey ignores it)

This works because the operad constrains which ports exist and which connections are valid. Ownership is structural: if `OBJ17.ports.provides_model` has `direction: "out"` and `targets: [{type: "OBJ06", port: "owned_by"}]`, then the provider OWNS its models through the port declaration.

### Hybrid Proposal (König at HG Meta-Layer)

Add wire-nodes **above** the kernel, at the HG layer:

```
Kernel layer:  Node ──wire(4-tuple)──→ Node     (current, unchanged)
                 ↓ lossless bijection (König's theorem)
HG meta-layer: Node ──edge──→ WireNode ──edge──→ Node   (bipartite)
```

**What König wire-nodes enable** (beyond the existing `Config` field, which is limited to flat key-value pairs on individual wires):
- Rich wire metadata (creation time, confidence score, evaluation result) as first-class node properties
- Wire-to-wire morphisms (one relation referencing another)
- HG-layer queries that treat wires as first-class citizens
- HDC encoding: `φ(wire_node) = SRC_ROLE ⊗ φ(source) ⊕ TGT_ROLE ⊗ φ(target) ⊕ ...`

**What doesn't change:**
- Kernel internals (`cat.Wire`, `WireKey`, `ValidateLink`) — untouched
- The 4 NTs — LINK still creates a 4-tuple wire at kernel level
- Operad validation — still operates on typed ports
- Morphism log format — still records LINK/UNLINK with 4-tuple

**The König layer is a view**, not a replacement. It's the HG functor applied to kernel state — the same lossless bipartite encoding proven in `hypergraph.md` Proposition 2. The kernel doesn't know about wire-nodes; the HG layer generates them from kernel state.

### Explorer Implications

When the König layer is implemented, the Explorer gains the ability to show wire-nodes as clickable entities with their own detail panels — metadata, provenance trail (which Actor created this wire, when, as part of which program), and connections to other wires. This transforms the Explorer from showing "A connects to B via port P" to showing "this relation exists as an entity with properties."

## §8 Paper Implications (ACT 2026)

The current paper (`main.tex`) covers: Container Category, 4 NTs, Authority Filtration, Stratum Filtration, Contravariant Orders (Galois connection), MCP bridge, System 3 reasoning, Benchmark functor.

**New material from this session for future paper sections:**

1. **Presheaf topos formalization** — queries as subobject classifiers, functors as geometric morphisms. Currently in `hypergraph.md` but not in the paper.

2. **König encoding proof** — the bipartite storage bijection and information efficiency. Proposition 2 from `hypergraph.md` deserves a paper section connecting it to the wire identity model.

3. **Multiway system section** — the implicit multiway system, three pruning steps, governance as observer. Connects mo:os to Wolfram Physics Project. Theoretical — doesn't require implementation to state.

4. **Enforce/discover as reducibility boundary** — maps the stratum model onto Wolfram's computational reducibility/irreducibility distinction. Strengthens the paper's connection to physics of computation.

5. **HDC structure-preserving functor** — `F_HDC : C → H` where bind/bundle/permute preserve graph topology. Currently in `hypergraph.md` Pillar 3, not yet in paper.

**Not for paper (implementation-only):** König wire-node OBJ type, Explorer redesign, QUIC stream mapping, promoted projection mechanics.
