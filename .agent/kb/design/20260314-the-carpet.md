## The Principle

```
state(t) = fold(log[0..t])
```

Four invariant natural transformations — ADD, LINK, MUTATE, UNLINK — are the generating morphisms of a free category. Everything else is either an object in the resulting graph or a structure-preserving functor (model) applied to it.

There are only two things: **syntax** and **functors**.

---

## 1. Syntax and Semantics Are Different Things

Gu & Zanasi (CALCO 2021, "Functorial Semantics as a Unifying Perspective on Logic Programming") prove that different flavors of logic programming — classical, probabilistic, weighted — share the **same syntax category** (SynLP, freely generated from program clauses as string diagrams). The difference is only in the **semantic functor** — the structure-preserving map to a target category:

| Flavor | Functor | Target category |
|--------|---------|-----------------|
| Classical LP | ⟦-⟧ : SynLP → **Set(2)** | Boolean algebra |
| Probabilistic LP | ⟦-⟧ : SynLP → **Stoch(2)** | Stochastic matrices |
| Weighted LP | ⟦-⟧ : SynLP → **Set(K)** | Semiring-valued sets |

The syntax stays fixed. Only the model changes. And correspondences between *different formalisms* (e.g., probabilistic logic programs ↔ Bayesian networks) can be expressed **purely at the syntactic level** via translation functors between syntax categories — without reasoning about semantics at all.

## 3. Two Webs — Semantic and Functorial

### The Semantic Web (syntax side)

`ontology.json` — types, ports, constraints, the operad registry. This is SynLP: the inferential structure of programs. The grammar. It says what compositions are *valid*. It does not say what they *mean*.

This is what the industry calls "semantic" but is actually **syntactic** — schemas, types, validation rules, protocol contracts. All syntax. All the operad.

### The Functorial Web (semantics side)

FUN01–FUN05, plus every projection, pipeline, and transport mapping. These are the *models* — they assign meaning to syntactic structures by mapping them into concrete domains:

| Functor | Domain → Codomain | What meaning it assigns |
|---------|-------------------|------------------------|
| FUN01 FileSystem | Manifest → C | File tree structure |
| FUN02 UI_Lens | C → React | Visual rendering |
| FUN03 Embedding | payload → ℝ^n | Vector similarity |
| FUN04 Structure | subgraph → DAG | Dependency ordering |
| FUN05 Benchmark | Provider → Met | Performance equivalence classes |

The meaning changes depending on which functor you apply. The syntax stays fixed. Different users, different deployments, different GPUs, different social topologies — all are different models (functors) applied to the same syntactic structure.

**The decoupling IS the categorical separation.**

## 4. Why Industry "Skills" Don't Scale

From the manuscript: *"PURPOSE SHOULD BE: TO USE AND TO PRODUCE KNOWLEDGE"*

Industry "skills" / "tools" / "workflows" / "agents" operate at the metadata level — describing what boxes do via docstrings, use-case examples, intent labels. This is stickers on boxes. The logic inside the box is a string diagram in a syntax category. You cannot reason about composition from stickers. You CAN reason about composition from the syntax category, because the CDMU equations guarantee well-defined composition.

Task decomposition without considering the internal morphism structure is **inherently incomplete** — the person who gives the task cannot predict all outcomes unless they know the syntax (the code, the graph structure, the composition rules). This is not a tooling problem. It is a categorical problem: metadata is in Set (flat, unstructured), while composition lives in the free CDMU category (structured, with equations).

The solution is not better metadata. It is **functorial composition**: define the syntax, then apply models. The models ARE the meaning. The syntax IS the structure. Don't layer semantics on top of syntax — let functors bridge them.

## 5. Infrastructure Carrying Code

**Terraform:** code → infrastructure (declarative descriptions generate infra).

**mo:os:** infrastructure ↔ code ↔ infrastructure (the graph carries code as leaves; stable patterns get promoted back into the kernel as compiled Go).

The kernel self-seeds: `SeedIfAbsent("urn:moos:kernel:self")`. It enters its own graph. It is simultaneously:
- **The fold** (the process that produces state)
- **A node** (an object in the state it produced)
- **An actor** (a URN in the envelopes it applies)

This is Gu & Zanasi's **traced extension** (Section 3.3): feedback wires create fixed points. The Herbrand model is the least fixed point of T_P with traces. Promoted projections ARE feedback wires — the system's output feeding back into its own syntax.

The 5 kernel colors (runtime_surface, protocol_adapter, system_tool, infra_service, agnostic_model) are promoted projections: patterns that started as graph structure and became compiled functions. The kernel sub-operad IS the set of promoted projections. When a new category stabilizes, it migrates from "data in graph" to "code in kernel" — the adjunction Include_K ⊣ Restrict_K grows by one color.

## 6. Discovery Cost vs Retrieval Cost

From the manuscript, formalized:

- **Knowledge discovery cost ∝ |E|** (edges in subgraph) — exploring inferential structure
- **Information retrieval cost ∝ |N|** (nodes in subgraph) — looking up known atoms
- **Subgraph complexity = |E| / |N|** — ratio of syntax to data

This maps to the Gu & Zanasi distinction between the *dependency graph* (edges = clauses = inferential relationships) and the *atom set* (nodes = ground data). Discovery is edge-heavy because you are traversing the syntax category. Retrieval is node-heavy because you are evaluating the model at known atoms.

The delta between discovery cost and retrieval cost IS the delta between syntactic analysis and semantic evaluation — between "what can compose" and "what does it mean."

Pipeline optimization: reduce discovery cost by finding the ideal subgraph index (the morphism structure), then retrieval becomes cheap (just the nodes at known addresses). This is why the fold is efficient: once the syntax is known (the log), evaluation (the fold) is linear in log depth.

| Functors (FUN01–05+) | Models assigning meaning | ⟦-⟧ : SynLP → Sem |
| HTTP/3, QUIC, WebRTC | Transport = monoidal structure | Tensor product ⊗ in CDMU |
| Other kernels in H | Different programs over related atom sets | Different logic programs ℙ', ℙ'' |
| Industry landscape | External syntax category | SynBN_G |
| Superset | Translation functor | ℱ : SynBN → SynLP |

Everything is simpler because syntax and functors are independently variable. The "smoothing" of the complex hypergraph IS the categorical separation. Any object is shareable because identity is URN-based (content-addressable in future). Decoupling is structural, not architectural.

Between OS and user (filesystem, human input, social structures) and structured internet (HTTP/3, distributed kernels): the kernel sits as I/O fanout — parsing external into envelopes (I-side), projecting state into external (O-side). The middle is for users/groups/admins to hydrate. The I and O sides are promoted projections — compiled category theory.

## 9. Implications for the Paper

The ACT 2026 paper thesis should be:

> `state = fold(log)` with 4 invariant natural transformations is sufficient for sovereign AI infrastructure. The ontology is a syntax category in the sense of Lawvere's functorial semantics. Projections are models — structure-preserving functors to target categories. The correspondence between industry formalisms and kernel structures is purely syntactic, established by translation functors, not by semantic reasoning.

Three figures:
1. **The syntax/semantics separation** — ontology (SynLP) with multiple functor arrows to target categories (React, Met, ℝ^n, DAG, Manifest)
2. **The self-seeding trace** — kernel as node in its own graph, feedback wire creating the fixed point
3. **The three-layer tower** — Industry (SynBN) → Superset (SynLP) → Kernel (promoted projections), connected by translation functors

## 10. The Carpet

The rug that ties the room together:

**There is a free category (the ontology). There is a fold (the kernel). There are models (the functors). Syntax is fixed. Semantics is variable. Everything else — transport, storage, UI, agents, benchmarks, social graphs, industry landscapes, code, files, users — is either an object in the free category or a functor image of one.**

One principle. Everything derives.
