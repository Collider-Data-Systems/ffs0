## Memory allocation — categories and functors, not just "where data lives"

You asked about GPU vs CPU vs disk vs hypergraph — this is the right question. The answer is functorial.

**The same syntax (the ontology, the graph) maps to different target categories via different functors. Each target category corresponds to a memory domain:**

| Functor | Source | Target category | Physical memory | Character |
|---------|--------|----------------|-----------------|-----------|
| Identity (KER) | Graph state | `GraphState` struct | CPU RAM | Hot, mutable, RWMutex-guarded |
| FUN01 FileSystem | Graph → files | Manifest category | Disk (JSONL, JSON) | Cold, persistent, append-only |
| FUN03 Embedding | Node payloads → vectors | ℝ^1536 (or ℝ^d for HDC) | GPU RAM | Massively parallel, bind/bundle/permute |
| FUN02 UI_Lens | Graph → React | Browser DOM | Client RAM | Ephemeral S4 projection |
| FUN05 Benchmark | Providers → metrics | Metric space Met | CPU (computed on demand) | Classification functor |
| (planned) Postgres store | Graph state | Relational tables | Disk (indexed) | Durable, queryable |
| (HDC) F_HDC | C → H | Hypervector space {-1,+1}^d | GPU RAM | Structure-preserving, algebraic |

**The key insight you're pushing toward:** runtime memory is NOT a flat address space. It's a **coproduct of target categories**, each with different computational characteristics:

- **CPU RAM** — where the fold runs. Sequential, mutex-guarded, deterministic replay. This is the KER layer. Go's garbage collector manages it. Rust would give you manual control but at the cost of lifetime annotations everywhere — for a graph with dynamic wire topology, Go's GC is actually the right tradeoff because node/wire lifetimes are unpredictable (they depend on UNLINK morphisms from arbitrary actors).

- **GPU RAM** — where HDC/VSA functors would run. The bind⊗/bundle⊕/permute π operations are embarrassingly parallel. A node's hypervector φ(node) = ⊕{w : w ∈ wires(node)} is a map-reduce over its wire set. This is FUN03 upgraded from flat embeddings to structure-preserving hypervectors. GPU locality matters: you want the full wire-set in VRAM before computing φ. That's a **subgraph materialization** problem — you need `ScopedSubgraph(actor)` but projected into VRAM, not CPU RAM.

- **Disk** — the morphism log. Append-only, the source of truth (AX3). The fold reconstructs CPU state from it. This is the cheapest memory but the slowest. The planned Postgres store would add indexing (by URN, TypeID, timestamp) without losing append-only semantics.

- **The hypergraph H itself** — this is the abstract mathematical object. It doesn't "live" in one memory domain. It's the **colimit** of all its physical representations. The kernel's CPU state is one functor image. The GPU vectors are another. The disk log is another. They're all consistent because they're all projections of the same syntax through different functors. Consistency is guaranteed by the catamorphism — replay from log produces the same state regardless of which functor you apply afterward.

**Go vs Rust for this:**
Go is correct for the kernel right now because:
1. GC handles the dynamic graph topology (nodes/wires created/destroyed by morphisms at runtime)
2. `sync.RWMutex` is exactly the concurrency model you need for single-kernel sovereignty
3. Zero external deps keeps the trust boundary clean

Rust would matter if:
1. You need zero-copy wire processing (network I/O → kernel → GPU without allocation)
2. You want to control GPU memory layout explicitly (CUDA interop)
3. Federation at H level needs kernel-to-kernel message passing without GC pauses

The promotion pattern (stable S4 → compiled kernel code) is where Rust's advantage would emerge — promoted projections are **hot path code** where allocation control matters. But that's v0.3.0+ territory.

## Gu & Zanasi connection to memory/runtime

You asked to check the paper. Here's the connection you're sensing:

Gu & Zanasi prove that **SynLP** (the syntax category of logic programs) is the **same** regardless of which semantic functor you apply. Boolean logic, probabilistic logic, weighted logic — all share the same syntax. Only the model (the functor to a target category) changes.

**For mo:os memory allocation, this is the exact same pattern:**

```
Same syntax (ontology + graph state)
    │
    ├──→ F_cpu:  C → Go structs    (CPU RAM, RWMutex, sequential fold)
    ├──→ F_gpu:  C → {-1,+1}^d    (GPU VRAM, bind/bundle/permute, parallel)
    ├──→ F_disk: C → JSONL lines   (disk, append-only, the causal trace)
    ├──→ F_net:  C → protocol frames  (network, HTTP/3 QUIC streams, distributed)
    └──→ F_ui:   C → React DOM     (browser, ephemeral S4 projection)
```

**"Running code" = applying a semantic functor.** The fold `Evaluate()` is F: Syn → Sem — it takes syntax (an envelope) and produces semantics (new state in a target category — CPU RAM).

**"Inspecting code" = traversing the syntax category.** The Explorer, the UI_Lens, the scoped subgraph queries — these stay in Syn. They never cross into Sem. That's why they're S4 (read-only projections). They are NOT running the fold; they're walking the syntax graph.

The difference between running and inspecting IS the syntax/semantics separation. And the choice of GPU vs CPU vs disk vs network is NOT a performance optimization — it's a **choice of target category**. Each has different algebraic properties:

| Target category | Product (⊗) | Coproduct (⊕) | Monoidal structure |
|----------------|-------------|----------------|--------------------|
| CPU (Go structs) | struct composition | interface dispatch | Sequential (mutex) |
| GPU (hypervectors) | bind (XOR/multiply) | bundle (add+threshold) | Parallel (SIMD) |
| Disk (JSONL) | line concatenation | file merge | Append-only |
| Network (QUIC) | stream multiplexing | datagram fanout | Causal invariance |

**This is why Go vs Rust matters at the functor boundary, not inside the syntax.** The syntax category (cat package, fold package) is pure — it doesn't care about memory. The choice of runtime (Go GC vs Rust ownership) only matters when you cross into a specific target category. Go's GC is fine for F_cpu. Rust's ownership would matter for F_gpu (zero-copy CUDA interop) and F_net (zero-allocation protocol parsing).

Your three points

**1. Promotion is about lifecycle, not just I/O proximity.**

You're right — I was too narrow. Any stable projection of the superset category that has been validated through use (S3 evaluated, patterns consolidated) is a candidate for promotion to compiled Go code. The I/O boundary (transport, protocol parsing, file reading) is just the *first* place this happens because those categories stabilize earliest. But promotion is general:

- A kind that every deployment uses → promote from `ontology.json` instance to a Go type
- A morphism pattern that always composes the same way → promote from `Program` to a Go function
- A validation rule that never changes → promote from operad registry to compile-time check

The lifecycle dimension: a promoted projection has **longer persistence** than a graph node. Graph nodes live until UNLINK. Compiled Go code lives until `go build`. That's a different durability category — not disk vs RAM, but **change frequency**. Promoted code changes on admin git push cycles. Graph nodes change on user morphism cycles. The adjunction Include_K ⊣ Restrict_K captures this: Restrict_K projects the graph into the kernel's compiled subset, Include_K embeds the kernel back into the graph as a node.

**2. The graph IS the zero-copy structure.**

Yes. GraphState is already `map[URN]Node` and `map[string]Wire` — pure value types with no allocations beyond the map entries themselves. An envelope arrives, the fold produces new state, the old state is GC'd. The "wire processing" between network I/O → kernel → GPU is just: parse envelope from HTTP body (allocation #1), call `Evaluate()` (allocation #2: cloned state), persist to log (allocation #3: JSON encoding). Three allocations per morphism. The graph structure itself — the topology of who points to whom — is literally pointer-free. URN strings are the addresses. That's already content-addressable in structure if not in name (SHA URNs would make it literal).

For GPU: the HDC functor would read the wire map, compute bind/bundle/permute, and write to VRAM. The graph doesn't move — the functor projects it. Zero-copy in the sense that the source (graph) is never modified by the projection.

**3. Workstation runs kernels, plural.**

Correct. `urn:moos:workstation:hplaptop` is not a kernel — it's a **compute resource** (OBJ10 in the ontology) that CAN_SCHEDULE kernel instances. A workstation might run:
- One kernel for your personal workspace
- Another kernel for a shared project
- A docker container running tools
- An Ollama instance running local models

Each is a separate process, each is a node in H, each has OWNS wires to its own subgraph. The workstation is the **scheduling context**, not the kernel itself.
