## TL;DR

- mo:os is an FP artifact whether or not it says so: `engine := fold(log)` is a left fold of a documented-pure algebra over an append-only free monoid. The kernel already ships catamorphism, copy-on-write immutability, envelope-level CAS, core/shell effect separation, and get-only optics — mostly under other names.
- CI-4 ("same log → same state, always") is initial-algebra uniqueness: determinism is a theorem, conditional on the algebra being pure. It isn't fully pure — `time.Now()` inside `fold.Evaluate` stamps `CreatedAt` at fold time (evaluate.go:51,:84), so replay holds only modulo struct timestamps. Best single fix in this note.
- The operad is our ADT layer with the checks moved to gate time — and the gates have named holes: additive-MUTATE bypasses `mutate_scope` (F-a), enum `Values` are loaded but never enforced, and the port-color gate fails open on 69 hardcoded literals (#50). Illegal states are representable wherever the gate isn't.
- The rewrite log is a **free monoid**, not a free monad — no result-binding, all URNs caller-supplied. Genuine free-monad structure in 4.0 doctrine is Poly p-trees, a different object **(conjecture)**.
- Testing is 100% example-based today; zero PBT anywhere in moos-kernel. Every doctrine sentence containing "always"/"never" is an unwritten property; the operad registry is a ready-made generator oracle.
- Time-travel (`GET /fold?to=n`) is architecturally free, not computationally free — a TARDIS with O(log-length) fuel cost per trip.

## purity-immutability

The idea: immutability = never change in place; the append-only log with derived state is that pattern at system level. Both halves are codified in types, not just doctrine: GraphState is documented DERIVED with `state(t) = fold(log[0..t])` (state.go:3-8), and `fold.Evaluate` is clone-before-mutate with original-state-on-failure (evaluate.go:10-17). Discipline is deep-copy-on-write today — `Clone` deep-copies Nodes, Relations, and all three indexes per apply; COW is flagged as future perf work with correctness deliberately first (state.go:84-90). No in-place log edits exist: LogStore's data ops are Append and ReadAll only; grep Truncate|compact|O_TRUNC under internal/ = zero. The single-writer log_seq guarantee holds **in the default configuration**, with three documented weakenings: unix flock is advisory only; `--allow-shared-log`/`NewSharedLogStore` is an explicit "UNSAFE ... emergency escape hatch"; no-lock platforms silently fall back to shared (log_store.go:16-63).

Write-ahead ordering holds in `applyWithOptions`: Append before `rt.state = next`; persist failure leaves state untouched (a seq gap remains from the pre-incremented counter). The swap is a constant-time struct assignment of five map headers under the write lock — cheap and lock-atomic, not literally a pointer swap (runtime.go:186-244; state.go:22-33).

Time-travel is architecturally free, not computationally free: `GET /fold?to=n` runs a fresh full `fold.Replay(log[:n])` per request, no snapshot caching (server.go:224-265).

The known leak: `time.Now()` in applyADD/applyLINK means replayed `CreatedAt` differs from the original run — CI-4 holds for topology, properties, Version; not for Go-struct timestamps. Doctrine compensates: governed `created_at` is an explicit immutable property, "NOT runtime-injected" (moos-rewrite-envelope SKILL.md:57).

**(conjecture)** HAMT-style persistent maps would cut Apply from O(total entries) to O(log n) per touched entry with unchanged fold semantics, at the cost of a materialization step for the `(nodes, relations)` wire shape. Direction asserted in the TODO; win unmeasured — zero benchmarks in repo.

## folds-recursion-schemes

The fold is literal code: `fold.Replay` = foldl of `Evaluate` over persisted entries from empty state, run once at boot (replay.go:23-39; runtime.go:59-68); doctrine D6 `engine := fold(log)` landed v4.0.0 (ffs0/AGENTS.md:79). Recursion-scheme reading: the log is the free monoid E* over Envelope; Evaluate is a monoid action; CI-4 is exactly initial-algebra uniqueness — fix the algebra and the catamorphism is unique. Determinism is a theorem *provided the algebra is pure*, which it currently isn't (the CreatedAt leak above; the CI-4 test only passes because it compares URN/TypeID — fold_test.go:305-321).

Boundary discipline is clean: operad validation and §M11/§M12 gates are admission control at append time, deliberately outside the fold algebra — "Replay is prospective-only", pre-gate logs rebuild identically (evaluate.go:14-16; moos-kernel CLAUDE.md).

Fusion is half-exploited: the three secondary indexes are maintained inline in Evaluate with `Rebuild()` as the from-scratch spec (evaluate.go:57,:89,:151; state.go:53-75). The fusion law `Rebuild(fold(log)) == foldWithIndexes(log)` is a testable equation the two code paths silently share — no test asserts it today. Partial fold is on the wire (`/fold?to=n`, SSE checkpoint law) but boot never checkpoints. Per-step cost is O(|state|) via deep Clone; the TODO's fix is incrementalizing the fold step (O(rewrites)), orthogonal to incrementalizing derived views.

**(conjecture)** Banana-split the HDC LiveIndex into the carrier (product algebra GraphState × LiveIndex), replacing full `Recompute(state)` per apply (runtime.go:136,:810,:903) with per-envelope updates; correctness condition `Recompute(fold(log)) == fusedFold(log)`. The drift→claim feedback loop (re-Recompute after reactive emission, :903) makes the fused carrier non-trivially recursive — unproven.

## adts-illegal-states

The operad Registry is the ADT declaration layer: `NodeTypeSpec.Properties` (product side) and `RewriteCategorySpec.MutateScope` — source comment reads "exhaustive list of fields that may be changed under this WF" (registry.go:57; "fields" is the repo's word, a de-rot candidate — ours is *properties*). `ValidateADD` is a smart constructor: missing required immutables reject at node birth (validate.go:12-28). `fold.Evaluate` does the Go-idiom exhaustive switch with fail-closed default over the closed 4-variant rewrite sum (evaluate.go:22-33).

Then the holes. Envelope is a sum-as-product: 16 omitempty properties, per-variant presence checked but foreign-variant properties never rejected — an ADD carrying SrcURN/TgtURN passes (rewrite.go:27-61; evaluate.go:155-184). `mutate_scope` is capability typing **with a permissive default**: the scope check fires only for non-empty MutateScope; of ontology.json's 21 declarations only ~9 are non-empty lists — 10 null, 1 `[]`, and WF15's prose string is silently dropped to empty by the loader (validate.go:172-175; loader.go:69-75). F-a: the additive-MUTATE path skips rewrite_category and mutate_scope entirely (validate.go:128-159; running-state.md:15; queued on moos-kernel#50). The kernel depends on F-a — the sweep's firing_state MUTATE deliberately omits rewrite_category (sweep.go:156-190) — **but** firing_state appears in no WF's mutate_scope, so a scope-conditional fix or the g6c prune leaves the sweep intact; only a full closure breaks it without first giving firing_state a WF home.

Worst class: declared-but-unenforced. `PropertySpec.Values` (76 enum declarations) is loaded and consumed by nothing — `firing_state="banana"` would fold; t_hook transition order and F-c's at-most-one presents-as are doctrine-only (loader.go:130-131; validate.go:135-191; registry has no multiplicity slot). Illegal states representable at value, transition, and cardinality level.

**(conjecture)** Backward-compatible F-a fix: require rewrite_category on additive MUTATE when the property appears in any WF's mutate_scope, or prune deprecated properties (g6c). Replay-safe because gates are prospective-only.

## event-sourcing-free-structures

Event sourcing is the interpreter pattern applied to persistence: Envelope is a deep-embedded instruction over the closed 4-op signature (pure JSON data, rewrite.go:27-61), the log is the program, `Evaluate` the algebra, `Replay` the interpreter with idempotent-skip semantics per op (replay.go:41-53). Log-as-free-monoid is standing doctrine, not a new identification — M1/M3 in the T=187 categorical contract (categorical-contract.md:23,27).

The sharper point: the log carries **no monadic bind**. `EvaluateProgram` threads only state; step results never feed envelope construction; all URNs are caller-supplied — fold mints no identifiers (program.go:14-27; URN minting exists only in the kernel effect layer, outside fold). So free monoid, not free monad, is the correct identification — and the stronger consequence is free-applicative-style static analyzability: fixed program shape means envelope batches can be validated, linted, and diffed without interpretation.

**(conjecture)** "Log = free monad on the 4-op functor" holds only degenerately (no result-binding collapses the free monad to sequences); the genuine free-monad structure in 4.0 doctrine is Poly p-trees — repo/branch/worktree topology, "trees are free monads on polynomials" (poly-foundations.md:38-39,:96) — a different object from the log. The act2026 paper itself hedges ("conjecturally a Poly-comonoid").

Alternative interpreters exist at transport: `/fold?to=n` (prefix reinterpretation), `/fold/stream` (snapshot + increments), `/twin/ingest` (full re-interpretation on a peer engine incl. gates — server.go:224-277; twin.go:24-45). Current read models all factor through the fold rather than interpreting the log directly: HDC recomputes from folded state; the Julia F-projection lane "reads folded HG state and writes local files" (runtime.go:136,:810,:903; projections/README.md:28).

## effects-at-boundaries

Functional core / imperative shell, three floors down. Kernel floor: layer discipline is explicit — "graph has no IO; fold is pure; only kernel has effects" (moos-kernel CLAUDE.md; evaluate.go:10-17). Sweep floor: `SweepOnce` is deterministic given (state, currentT, actor, baseLogSeq, now), no IO, returns `[]graph.Envelope` as effect descriptions; `RunTimedSweep`/`SweepTick` is the interpreting shell — errors logged, not propagated, next tick retries, batch all-or-nothing (sweep.go:62-81,:259-295).

Staged interpretation — with a scope correction from verification. **TIME-driven** t_hook firing is effects-as-values: the sweep never auto-applies react_template; it ADDs a governance_proposal snapshotting the template and MUTATEs firing_state pending→proposed in one atomic batch; approved→applied is deliberately deferred (TODO at sweep.go:169-174), so that transition today is a manual admin MUTATE. **But the staging is not universal**: the EVENT-driven M6 pathway auto-applies react_template — reactive Engine pass 2 builds the proposal directly and `runReactive` applies it immediately at depth-1, no governance stage (engine.go:48-74; runtime.go:570-579). Idempotency is a visible state machine, not outcome-scanning: v3.11 replaced the O(proposals) scan with the O(1) `firing_state ∈ {"", pending}` predicate (sweep.go:69-96).

Divergent failure semantics between the two interpreters: sweep retries; `applyReactiveLocked` silently drops validation-failed, fold-failed, and persist-failed proposals with no logging (runtime.go:586,:591,:598,:610). Each behavior is documented at its site; the **cross-pathway** retry-vs-drop contract is documented nowhere.

Agent floor: boundary-act doctrine ("surface before doing", AGENTS.md:99 — that line's own wording is off-nomenclature, quoted as-is), dry-by-default projections with `--mode write` as the explicit actuator step, actuator-then-derivation per t187. **(conjecture)** "Side effects only at actuator leaves via channels" is doctrine, not kernel code — zero 'actuator' hits in moos-kernel; the ontology channel type models ingest, not dispatch; a kernel-mediated dispatch path is design intent, unbuilt.

## property-based-testing

Everything above that says "law", "invariant", or "by construction" is an unwritten property, and moos-kernel has zero PBT — no testing/quick, no pgregory.net/rapid, repo-wide (grep = zero). Current coverage is example-based: the t249 gate suites are 15 + 12 hand-enumerated envelopes against a throwaway :8899 kernel, verdict = `ok == expect_ok` (t249_gate_suite.py:62-108; phase2:66-113). Fold non-mutation is checked at exactly two hand-picked points (one ADD, one UNLINK — fold_test.go:39-42,:199-202), and TestCI4_ReplayDeterminism replays a 1-entry log twice comparing only URN/TypeID — shallow, not deep-equal (:305-321). Determinism over arbitrary logs: untested, and a textbook rapid property.

The substrate is ideal: state is a pure function of the generated input (the log), so fold determinism and replay equivalence are directly executable without mocking. Ready-made oracles: the log-integrity invariant `log_len - LogSeqMissing() == max_log_seq` (runtime.go:517-523) as a stateful-PBT step invariant; and the operad registry as a generator source — noting enforcement is split across `ValidateLINK` (pair declaration + port-color matrix, validate.go:42-83) and the state-aware `ValidateStrataLink` (WF-level and pair-level type constraints incl. `*` wildcard, :292-375), both reading the same ontology.json, with one generator caveat: WFs declaring no pairs at all are legacy-permissive, so near-misses against spec-absent WFs ACCEPT. Predicted-rejection gates (phase-2 D03/G04 "EXPECTED REJECT (gap …)") are single sample points of finite rejection regions a generator could sweep exhaustively.

**(conjecture)** Model-based PBT (doctrine-encoding Python model vs the :8899 kernel) would have surfaced the G15 at-most-one-presents-as gap automatically as model/SUT divergence. **(conjecture)** A Hypothesis generator can reuse the t249 harness's constructors (`post/prop/add/link/mut`) and endpoints — near-unchanged, modulo refactoring the script's import-time fixture side effect into an importable module.

### fp-in-go, compressed

Go enforces none of this; the kernel does FP by convention and mostly does it right — errors-as-values, value semantics + Clone, exhaustive switch with fail-closed default (evaluate.go:22-33), zero generics by stdlib-first choice. The one place it does it wrong is #50: `portColorFromName` is a 69-literal switch (68 colored + `bound-to` deliberately `""`) returning zero-value on miss — a partial function — and `ValidateLINK` swallows the resolve error, so unknown ports silently skip the §12.2 color gate (validate.go:220-248,:74-77). Doctrine-acknowledged: ontology.json:3168 says the mapping is hardcoded kernel-side, "fail-closed pending kernel#50"; only the matrix subsection is loaded (loader.go:101-104). The design direction is already ruled in the issue: data-driven port→color map from ontology.json, then coverage, then flip — branch `feat/color-gate-data-driven`. **(conjecture, remaining detail)** exact ontology shape: new `port_colors` map vs deriving from `declared_pairs_by_wf` (which already carries src_color/tgt_color, authored but unloaded). **(conjecture)** the flip should ship with a totality test over every declared port pair asserting both colors non-empty — coverage before flip, E3 principle (t249-wf20-round-package.md:33-35).
