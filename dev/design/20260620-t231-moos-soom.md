# mo:os ⊣ so:om — the engine and the surface matrix

> **Status: design draft (S0 → pending G-ingest). Conjecture-marked. GATE: prose only — this
> authorizes no ontology or URN change.** Authored T231 from a phone diary session (Keep widget,
> World Cup), reconciled against `kb/superset/ontology.json` (v3.16.2), the 4.0 drafts
> (`dev/design/20260605-t216-ontology-4.0-draft.md` D1–D5, `20260607-t218-manifold-instance-vocab-delta.md`
> D6–D8), and the `branch=F(session)` strategy (`20260607-t218-branching-strategy.md`).

## 0. The one sentence
**mo:os is the engine; so:om is the surface; they are an adjunction.** `mo:os` (Manifold Object
Operations Surface) is the durable data/graph layer — HG, instances, `state = fold(log)`. `so:om`
(Surface Operation Ontology Matrix) is the active-application surface layer — the live windows,
tabs, panes, widgets each user/agent touches. The engine projects onto the surface and ingests
back: **mo:os ⊣ so:om = F ⊣ G**, the same adjunction the system already runs, now named at both ends.

Two mascots, both `persona = Φ(purpose)` overlays (D3), never authority:
- **the dachshund (mo:os)** — the nose pointed at something; the fold/rewrite engine that powers
  the distributed graph and opens the dataspace to humans and AI.
- **the octopus (so:om)** — tentacles into the active environment (chat windows, Chrome tabs,
  office apps, the Keep widget) that record human/AI/group inference and inject it back.

## 1. mo:os ⊣ so:om = F ⊣ G (not new machinery — a name for what runs)
- `F: mo:os → so:om` (**project / lower**): fold the log, select a frame, render it onto active
  surfaces. This is `run-session-pipeline.ps1` and every dashboard/lens today.
- `G: so:om → mo:os` (**ingest / lift**): observe surface activity (a Keep note, a browser
  action) and reify it as typed nodes/rewrites. This is `moos-workspace-ingest` and the Keep-ingest
  runbook (`dev/reference/keep-ingest-runbook.md`).
- **mo:os is the only SOT.** so:om is **S0 projection substrate — observed-not-authored** (the D7
  surface layer). A window/tab/pane/widget is *where F lands*, never an authority node. This is the
  same status IDE conversations have had since the T173 pivot.

so:om is exactly the D7/D8 layer already drafted: surfaces named via `channel.kind ∈
{workstation-surface, virtual-desktop, window, tab-group, browser-tab, harness-pane, …}` and joined
to the semantic layer by `realizes` / `realized-by` (D8, observed-first). **Conjecture:** add
`keep-widget` (and other mobile surfaces) to the `channel.kind` set when the phone is modelled — a
D5 continuation, governance-gated.

## 2. The so:om matrix is indexed by a path-URN
The "matrix" is literal. Its **coordinate** is the tuple
```
(manifold × workspace × device × {agent | ∅} × user)  ↦  active surface
```
and the **cell value** is the `channel.kind` surface live at that coordinate. Sam's diary URN

```
urn:…manifold_mtdc . workspace_samsdiary . device_samsandroid . noagent . user_sam
```

**is a so:om matrix coordinate** — manifold→workspace→device→(no)agent→user, addressing the cell
whose value tonight is the Google Keep widget. The canonical kernel URN stays
`urn:moos:<type>:<short>`; the path-URN is the *surface address* (the matrix index), a so:om
projection of the underlying nodes, not a replacement for their URNs. (**Conjecture**, GATE: no URN
scheme change is authorized here.)

This is why the matrix "connects to the outer node, the edges on the operations surface": each cell
is the F-image of a node+its relations onto one device's active app — the edge of mo:os realized as
a surface.

## 3. The wiring — set → type → function → immutable → cache
The discipline Sam demanded ("don't buzzword — wire it"): **every set element is a `node`
(identity); every function is a `relation` (LINK = topology) or a `rewrite` (a WF op) — never a
method on an object.** The OOP world-model scaffold translates: `object → node`, `field →
property`, `method → relation / rewrite`. (Same ECS move as data-oriented design: entity/component/
system = node/property/(relation+rewrite).)

| set (Sam) | real type | function = relation / rewrite | immutable (set at ADD) | in active cache? |
|---|---|---|---|---|
| user | `user` ✅ | `user —WF02 delegates-to→ agent`; owns (WF01) | `owner_urn`, `name`, `urn` | — |
| group | `group` ✅ | collective principal; owns (WF01); `member-of` | `name`, `urn` | — |
| agent | `agent` ✅ | `workspace —WF19 has-occupant→ agent` | `owner_urn`, `delegate_type`, `urn` | occupancy (rotatable) |
| **device** | **MISSING ⚠ (conjecture)** | host of so:om surfaces; `device —realizes→ surface` (D8) | `hostname`, `owner_urn` | — |
| purpose | `purpose` ✅ | `workspace —WF19 has-purpose→ purpose`; φ steers rewrites | `slug`, `urn` | **φ(purpose) steering vector** |
| **soul** | `persona = Φ(purpose) = derivation` ✅ (D3) | `purpose —WF21 causes→ persona` (derived, never authority) | derivation provenance | **persona view (rebuildable)** |
| cycle | `clock` ✅ | embedding ∈ {linear, cyclic, dag, branching}; T-day/round/program-cycle | `epoch`, `embedding` | **current-T** |

**Immutables (CI-3 identity stability):** `owner_urn, created_at, name, urn`, and the **T-epoch**
(`2025-10-31T23:00:00Z` — the canonical fence-post; see §6). Set at ADD, never MUTATEd.

**Active-memory cache set** = the *derived, rebuildable-from-log* functions, held in RAM, **keyed by
graph identity and invalidated by rewrites** (the T194 HDC-FS-cache doctrine: rebuildable from
`log + ontology_version + encoder_version`). "Add the function to the cache" = register φ(purpose),
the persona view, current-T, etc., keyed by graph identity; drop them on the next rewrite. The cache
is never truth — it is a fold the engine keeps warm.

## 4. Two gaps the phone exposed
1. **`device` does not exist.** Everything today is a `workstation` — defined as a *kernel host*.
   But a phone is a **surface-only device**: it `realizes` so:om surfaces (Keep, WhatsApp) and hosts
   **no instance**. That is a genuine delta. **Conjecture (governance-gated):** either a new `device`
   node type, or `workstation.kind ∈ {server, mobile, surface-only}` distinguishing kernel-hosts
   from surface-only hosts. Either way the rule is: *a device realizes surfaces; only a workstation
   hosts an instance.*
2. **`noagent` is already legal.** WF19 `has-occupant` accepts a `user` (and `agent`, and `group`).
   A human-only workspace — Sam + the Keep widget, no agent in the room — is valid **as-is**. The
   diary lane `session:sam.samsdiary` with `has-occupant → user:sam` and *no* agent needs no new
   grammar. ✅

## 5. Branching = recursive F⊣G ingestion (the sharp insight)
Every **write** is an individual ingestion into an authority-ruled merger, **and the write is itself
a projection.** One shape at two layers:
- **Kernel layer:** a rewrite (ADD/LINK/MUTATE/UNLINK) is emitted by an actor into an *instance*;
  cross-instance reconciliation is the `twin_link` F⊣G sync + federation (WF16) — ruled by §M11/§M12
  liveness/permission gates and CI-5.
- **Repo layer:** a commit is emitted into a *branch* = `F(workspace)`; `merge branch→main =
  G(branch)` folds it into the shared SOT — ruled by **group/RBAC** (WF01 ownership + branch
  protection + CI-5 permission lattice). This is the `20260607-t218-branching-strategy.md` doctrine,
  re-derived from the write end.
- **The recursion:** the git write is `F(rewrite-intent)` landing on the **VCS surface**. Therefore
  **the repo is a so:om tentacle** (`channel.kind: vcs`), *not* the mo:os engine. "Writing to a repo
  is also the result of a projection" — exactly. The **merger** is the **colimit** over all writes:
  per-repo branches *and* per-instance folds that share a purpose-slug (t218 E4, `manifold = colimit`).
  The RBAC rule is the permission lattice gating **which generators land on `main`**.

> **Plainly: the kernel/HG is the only truth; every repo, branch, and `main` is a projection
> surface.** This is why `AGENTS.md` is "an F-image until generated" — the repo is so:om, not mo:os.
> (This very draft demonstrates it: it lands on its own branch `claude/moos-soom-design` because, by
> `branch = F(session)`, a distinct purpose-lane is a distinct projection that merges back under RBAC.)

## 7. Cross-model reconciliation (two Gemini reads, ingested T231)
Independent external triangulation — and where to keep discernment:
- **Corroborated:** mo:os=data/graph (dachshund), so:om=surface/IO (octopus), `F:M→O`;
  ECS = node/property/(relation+rewrite); **SSA = the immutable rewrite log** (CI-3/CI-4, WF21);
  LLVM-IR + "project the manifold onto sets" = F⊣G + the CI-2 projection registry. Two models
  re-derived the architecture unprompted.
- **Do not rebuild:** the dachshund **already exists** as `moos-kernel` (Go) + HG; Gemini's
  "state-machine graph in Next.js + Pydantic IR" reinvents the operad + port-color + §M11/§M12
  validation (now also surfaced in-editor by `moos-lsp`). The kernel operad is the only IR validator;
  Pydantic/Next live solely at the so:om edge.
- **Adopt for the octopus only (stack-neutral):** so:om is the frontend, so a JS surface stack is
  appropriate *there* — graph viz (ReactFlow / **Cytoscape**, already used), a **Chrome-extension
  sensor tentacle** (= the Antigravity browser agent = a G-ingest sensor), a reactive store
  (Zustand), and LangGraph for browser-side flows. Hardware split: Xeon/32 GB holds the warm running
  set; the RTX 3060 runs HDC/tensor (the T194 plan). **None of it is authority.** Listed as one
  option, not a commitment.
- **Pushback:** do not conflate the **render tick** (high-freq, lossy — so:om presence) with the
  **log commit** (durable, ordered — mo:os truth). They are two channels (§8), not one stream.
- **G1 (transport):** **WebTransport two-channel** — HTTP/3 **datagrams** for the lossy game-tick
  presence (cursors, live surface state) + reliable **streams** for the durable rewrite-log commits.
  Not WebSockets-or-event-driven; both, on one connection.
- **G2 (Agent↔User boundary on a shared Purpose):** not a type wall — an **authority gradient**.
  `user` = superadmin principal; `agent` = delegate with `P(delegate) ≤ P(principal)` (CI-5) +
  §M11/§M12. Both may `has-occupant` the **same** workspace and share one `has-purpose`. *Strict at
  the authority layer (who may emit which rewrite), permissive at the occupancy layer (both sit in
  the room).* The ontology already answers it.

## 8. The two-channel dataflow (so:om realtime)
| channel | carries | reliability | layer |
|---|---|---|---|
| HTTP/3 **datagrams** | cursors, presence, live surface deltas, the "game tick" | lossy, freshness > completeness | so:om |
| HTTP/3 reliable **streams** | rewrite-log commits, auth, joins, control | ordered, lossless (CI-4 replay) | mo:os |

The fixed-timestep/interpolation split of a game loop: the simulation (log) is deterministic and
reliable; the rendered presence is interpolated and lossy. Federation router (WF16) is the
coordinator; `twin_link` eager/lazy sync is the authority/rollback netcode.

## Conjectures vs settled
- **Settled (already in the ontology / drafts):** F⊣G projection/ingest; so:om = D7/D8 surface layer;
  `noagent` human-only occupancy; `soul = persona = Φ(purpose)`; `cycle = clock`; branching =
  `F(session)`/`G(branch)`; the authority gradient (CI-5/§M11/§M12); SSA = the rewrite log.
- **Conjecture (governance-gated, not applied):** `device` as a surface-only host (new type *or*
  `workstation.kind`); `channel.kind += keep-widget` / mobile surfaces; the path-URN as a formal
  so:om address; naming the whole surface layer "so:om" and the engine "mo:os".
